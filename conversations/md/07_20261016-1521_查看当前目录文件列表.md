## 3. Boot 版本获取方式：为什么是「生成后手工钉」

**背景**：计划钉死「Spring Boot 3.5.x，从 start.spring.io（Spring Initializr）生成」。但我实际去生成时发现 Initializr **已经不再提供 3.5.x**——现在它的版本列表里只剩 4.x（默认 4.1.1，另有 4.0.8 和 4.2 的预览版）。3.5 这条产品线对 Initializr 来说已下架；不过 Maven Central 上的 3.5.x 构件永远都在（我查到最新是 **3.5.16**）。

**为什么不干脆升到 Boot 4**：计划钉 3.5 不是随手写的。Boot 4 = Spring Framework 7 + Spring Security 7 + Jakarta EE 11，有一批破坏性变更（Security 配置写法、依赖坐标体系都变了）。阶段1 的 JWT 鉴权代码是按 Security 6 的 lambda DSL 写法规划的，社区资料、教程、排错答案也 overwhelmingly 是 3.x 体系。限时现场题里换大版本等于自找风险，所以「忠于计划的 3.5.x」优先于「接受生成器的 4.1.1」。

**具体做了什么**（这是「获取方式不同」的实指）：
1. 先用 Initializr 按 4.1.1 生成骨架——目的是拿到 `mvnw` wrapper、标准目录结构、`.mvn` 这些与版本无关的脚手架；
2. 手工把 `pom.xml` 里的 parent 从 `4.1.1` 改成 Maven Central 上查到的 `3.5.16`；
3. 这步有个隐藏坑：**Boot 4 生成的 pom 用了新依赖名**，比如 `spring-boot-starter-webmvc`（3.5 里叫 `spring-boot-starter-web`）、`spring-boot-h2console`（3.5 根本没有这个 starter）、`spring-boot-starter-webmvc-test`（3.5 里是 `spring-boot-starter-test`）。不改的话编译直接失败。所以我把整个依赖块按 3.5 命名重写了一遍，顺带补上 Initializr 本来就不提供的 jjwt 0.12.6，删掉 Boot 4 风格的 compiler 插件配置；
4. 最后用事实验收：`./mvnw package`、`./mvnw test`、连 MySQL 完整启动，全绿。

## Boot 为什么没有用最新版

先把「最新版」说清楚，这是关键：

| 版本线 | 最新版 | 我们用的 |
|---|---|---|
| Spring Boot 4.x（最新大版本线） | 4.1.1（Initializr 现在的默认） | 否 |
| Spring Boot 3.5.x（上一代稳定线） | 3.5.16 | **是，即此线终版** |

所以准确的说法不是「没用最新版」，而是：**站在 3.5 这条线的最后一个补丁版上，没有跳到 4.x 这条新线**。具体原因四个：

1. **Boot 4 是整代换底，不是常规升级**。它捆绑的是 Spring Framework 7 + Spring Security 7 + Jakarta EE 11 + Tomcat 11，底层 API 有破坏性变更。这不是推测——我生成骨架时亲眼看到的证据：Boot 4 的 pom 里连依赖坐标体系都重组了（`spring-boot-starter-web` 变成了 `spring-boot-starter-webmvc`，测试 starter 被拆散，还出现了 `spring-boot-h2console` 这类新模块名）。换到 4.x 意味着所有依赖、所有 Security 配置写法都要跟着换。

2. **阶段1 要写的 JWT 鉴权代码是按 Security 6 的写法体系规划的**（lambda DSL + `SecurityFilterChain` Bean 那套）。Security 7 又删掉了一批 API、调整了默认行为；一旦踩到差异，排错时能搜到的教程、Stack Overflow 答案几乎全是 3.x 体系的。限时现场题里，这种「写法对不上资料」的时间损耗是最亏的。

3. **对演示零收益**。评委看到的是页面和功能，Boot 3.5 还是 4.1 在演示效果上没有任何差别——没有任何一个题目要求的功能需要 Boot 4 才能实现。风险（迁移引入的坑）大于收益（版本号新一点）。

4. **为什么当时 Initializr 拿不到 3.5**：Initializr 只挂「仍在官方支持窗口内」的版本，3.5 线的 OSS 支持期已结束所以被生成器下架；但 Maven Central 上的构件永久存在。所以当时的做法是「生成器给 4.1.1 骨架（只为拿 mvnw wrapper 和标准目录）→ parent 手工钉回 3.5.16 → 依赖名换回 3.5 命名」。

一个已知的代价也告诉你：3.5.16 是 3.5 线的**终版**，以后不会再有 3.5.17 的补丁。对一个答辩后就封存的演示项目这不构成问题；如果这个项目演示后要长期演进，到那时再升 4.x 也不迟——但那应该是一次专门安排的迁移（改 parent + 换全部依赖名 + 重写 SecurityConfig + 全量回归），而不是现场赶工时顺手做的事。我的建议：本题保持 3.5.16 不动。
